# BScript — устройство виртуальной машины `bsvm`

Документ описывает, как устроена и почему так устроена виртуальная машина BScript фазы 1 (`bscript/vm/`). Язык описан в «BScript — спецификация языка» (`bscript_spec_ru.md`), формат файла `.bsc` и команды — в «Формат байт-кода BScript», версия 1 (`bscript_bytecode_ru.md`). Здесь — всё, что между ними: память процесса, значения и объекты, интерпретатор, куча и сборщик, дальняя память, оверлеи, ввод-вывод, сборка и измерения.

`bsvm` написан на B16, работает под монитором CPU16 и занимает 27,6 КБ резидентного образа (32,3 КБ с данными) плюс 21,1 КБ оверлеев в `bsvm.ovl`.

## 1. Исходники

| Файл | Содержание |
| --- | --- |
| `types.b16` | структуры `Val`, `Obj`, `Slot`, `Frame`; раскладка данных объектов; номера оверлеев |
| `bsvm.b16` | точка входа: перенос стека, загрузка, раскладка ближней памяти, запуск функции 0 |
| `interp.b16` | регистры интерпретатора, вызовы и возвраты, режимы вызова, раскрутка ошибок |
| `ops.b16` | команды байт-кода и таблица диспетчеризации `ops`, цикл `run` |
| `value.b16` | теги и типы, равенство, `str(x)`, объекты-ошибки и тексты ошибок |
| `heap.b16` | handles, выделение, функции доступа, барьер записи, сборка ближней кучи, массивы и куски |
| `map.b16` | словари: хеш-таблица с порядком вставки |
| `io.b16` | таблица потоков и файлов, буферы, построитель строк, обработчик Ctrl+C |
| `lib.b16`, `libstr.b16` | резидентные встроенные функции и методы; таблицы `bfuncs`, `mt_str`, `mt_arr`, `mt_map`, `mt_file`, `mt_err` |
| `ovl.b16` | менеджер окна: кадр модуля, кадры кода, загрузка и вызов оверлеев |

| `ov_fs.b16` | оверлей `fs`: пространства `fs` и `path` |

| `ov_gc.b16` | оверлей `gc`: переход в расширенный режим, перенос, полная сборка, выделение в дальней памяти, `fail`, `error()` |
| `ov_common.b16` | общее для `fs` и `sys`: пути-аргументы, открытие с повтором после сборки, чтение файла целиком |

Общие с компилятором определения — `common/bsdefs.b16` (формат `.bsc`, коды команд, номера встроенных функций и методов) и `common/util.b16`.

## 2. Память процесса

`bsvm` запрашивает `max_top = $C000`. Адресное пространство CPU16 — восемь страниц по 8 КБ; VM использует их так:

| Страницы | Адреса | Назначение |
| --- | --- | --- |
| 0–4 | `$0000–$9FFF` | резидентная часть, аргументы, стек B16, таблицы модуля, стек значений, handles, ближняя куча |
| 5 | `$A000–$BFFF` | продолжение ближней кучи; в расширенном режиме — окно данных дальней памяти; при запуске — окно загрузчика `init` |
| 6 | `$C000–$DFFF` | окно кода и оверлеев: обычно кадр модуля или текущий кадр кода, на время вызова — кадр оверлея |

Раскладка собственной памяти снизу вверх:

| Область | Размер | Где задано |
| --- | --- | --- |
| резидентная часть: код, данные, bss, буферы потоков и файлов | 32,3 КБ (код 23,9 КБ, данные 8,4 КБ, из них буферы 2,3 КБ) | — |
| блок аргументов командной строки | до 300 байт | монитор |
| стек B16 | 1,5 КБ (`CSTACK`), измеренный максимум около 1 КБ | `bsvm.b16` |
| таблица исходников и константы модуля | по размеру `.bsc` | `ov_init.b16` |
| таблица функций и таблица кадров (только у модуля больше 8 КБ) | по размеру + 800 байт | `ov_init.b16` |
| глобальные переменные | 4 байта на глобальную | `bsvm.b16` |
| таблица «номер константы → handle» | 2 байта на константу | `bsvm.b16` |
| стек значений | 384 значения, 1,5 КБ (`VSMAX`) | `bsvm.b16` |
| таблица handles | 3 байта (адрес и сегмент) на каждые 22 байта кучи | `heap_init` |
| ближняя куча | остаток до `$C000` (в расширенном режиме — до `$A000`) | `heap.b16` |

**Стек B16 перенесён.** `main` в `bsvm.b16` сразу переключает `SP` на область за блоком аргументов (`onstack`) и вызывает `vm_main`. Под `max_top` стек оставлять нельзя: страница 5 должна быть свободна, чтобы стать окном данных.

## 3. Запуск

1. `io_init` заполняет записи потоков 0–2 и через `HINFO` запоминает, какие из них — консоль.
2. `ovl_init` строит путь `bsvm.ovl`: `argv[0]` с расширением `.ovl` вместо `.cx`.
3. `init_run` выделяет кадр (`XALLOC`), ставит его на страницу 5, читает туда образ `init` и вызывает `vm_load`. После возврата страница 5 возвращается собственному кадру, а кадр загрузчика освобождается. Загрузчик выполняется один раз и места в окне 6 не занимает.
4. `vm_load` читает заголовок `.bsc`, проверяет сигнатуру `BSC1` и версию и раскладывает модуль (разд. 3.1). Ошибка — сообщение `bsvm: путь: текст` и код 126.
5. `vm_main` размечает ближнюю память, создаёт таблицу handles и кучу, обнуляет глобальные, регистрирует константы как статические объекты (`hstatic`), строит массив `args` в глобальной 0.
6. Ставится обработчик `EVT_BREAK` (`ONEVENT`), вызывается функция 0 в режиме `MODE_DISCARD`, и управление уходит в цикл `run`. Обратно оно не возвращается: программа завершается через `do_exit`.

Запуск пустого сценария стоит около 186 тыс. команд CPU16, через `bs` с годным кешем — около 250 тыс.

### 3.1. Размещение модуля

| Случай | Таблица функций и код | Таблица кадров | Константы |
| --- | --- | --- | --- |
| функции + код + 800 байт ≤ 8 КБ | кадр модуля в окне 6 | там же | ближняя память |
| больше 8 КБ (`cf_multi`) | таблица функций — в ближней памяти, код — до 4 кадров (`CF_MAX`), до 32 КБ | ближняя память | ближняя память |
| после констант осталось бы меньше 6 КБ кучи, а констант не меньше 2 КБ | как выше | как выше | статические сегменты дальней памяти; программа сразу в расширенном режиме |

Таблица строк не загружается: место ошибки ищется чтением `.bsc`, только когда оно нужно (`ov_sys.b16`).

Константы-строки в файле уже имеют формат объекта кучи (заголовок «тип, длина, 0» и байты), поэтому VM использует их прямо в памяти модуля: `hstatic` выдаёт handle, ставит флаг `F_STATIC` и вписывает номер handle в заголовок. Сборщик статические объекты не двигает и не освобождает: они лежат ниже `heap_lo`.

## 4. Значения и объекты

### 4.1. Значение

```text
struct Val { v: uint; t: uint }      // слово 0 — образ или ссылка, слово 1 — тег
```

| Тег | Тип |
| --- | --- |
| `$8000` | null |
| `$8001` | bool (0/1) |
| `$8002` | int (16-битный образ) |
| `$8010` … `$8014` | строка, массив, словарь, файл, ошибка: в `v` — ссылка на объект |
| `$0000–$7FFF` | не используется; оставлено для `ulong` фазы 2 |

Значение помещается в 4 байта и копируется двумя словами. Проверка «значение — объект» — одно сравнение `t >= $8010`.

### 4.2. Объект кучи

```text
struct Obj { fl: uint; size: uint; h: uint }   // 6 байт, затем данные
```

| Биты `fl` | Смысл |
| --- | --- |
| `$00FF` | тип: 3 строка, 4 массив, 5 словарь, 6 файл, 7 ошибка; 8–10 — куски (разд. 7.5) |
| `$8000` `F_MARK` | помечен сборщиком |
| `$4000` `F_SCAN` | помечен, но не просмотрен: стек пометки был полон |
| `$2000` `F_STATIC` | константа модуля |
| `$1000` `F_REM` | объект в списке барьера записи |
| `$0800` `F_DEAD` | данные перенесены в дальнюю память, место — мусор |
| `$0400` `F_CHUNK` | данные массива или словаря — в кусках |

`size` — размер данных в байтах; в памяти объект выровнен до чётного. `h` — номер handle: по нему сжатие исправляет таблицу handles.

**Данные по типам** (смещения от начала данных):

| Тип | Раскладка |
| --- | --- |
| строка | байты `0…size−1` |
| массив | `0`: длина; `2 + 4i`: элемент `i` (`Val`) |
| словарь | `0`: count, `2`: used, `4`: cap, `6`: nb; с `8`: записи по 8 байт; затем корзины |
| ошибка | `0`: код, `2`: текст (ссылка), `4`: объект (ссылка или 0), `6`: смещение кода места (`$FFFF` — нет) |
| файл | `0`: номер записи таблицы файлов (0 — закрыт), `2`: путь (ссылка) |

## 5. Интерпретатор

### 5.1. Регистры

| Переменная | Смысл |
| --- | --- |
| `ip` | адрес следующего байта команды (в окне 6 или в кадре модуля) |
| `vs`, `vsp`, `vlim` | начало, вершина и предел стека значений |
| `fbase` | первый локальный слот текущей функции |
| `glob`, `nglob` | глобальные переменные |
| `frames`, `nfr` | таблица кадров вызовов и их число |
| `konst` | номер константы → handle |
| `cur_err` | регистр «текущая ошибка» (ссылка или 0) |
| `bbase`, `bnargs`, `bn` | аргументы, их число и число результатов встроенной функции |

### 5.2. Цикл команд

```text
fn run() {
    loop {
        var p = ip
        var o = uint(*p)
        ip = p + 1
        if o > OP_LAST { op_bad() }
        ops[o]()
    }
}
```

`ops` — таблица из 65 указателей на функции, по одной на код команды; неиспользуемые коды ведут в `op_bad` (`bad instruction`). Операнды команда читает сама (`rd8`, `rd16`). Горячие команды (`ldl`, `stl`, `ldg`, `int8`) написаны без вызова `push`, с одной проверкой предела стека. Средняя цена — около 59 команд CPU16 на команду байт-кода.

**Безопасные точки.** После `jmp` (переход назад в цикле), вызова, возврата и встроенной функции проверяется флаг `promote_pending`: если он поднят, выполняется перенос в дальнюю память (разд. 7.3). Между командами все ссылки лежат на стеке значений, в глобальных и в объектах, поэтому ссылки можно менять.

### 5.3. Вызовы и кадры

```text
struct Frame { ret: uint; base: ptr Val; fnum: uint; mode: uint }   // 8 байт, до 100 кадров
```

`call_fn(f, mode)`: аргументы уже на стеке; база кадра — `vsp − число параметров`. Проверяются предел кадров и место на стеке значений (`stack overflow`), затем аннотации параметров, если у функции есть флаг проверки. Остальные локальные слоты заполняются `null`, `ip` ставится на код функции.

`op_ret(n)`: проверяет аннотации результатов, копирует `n` результатов на место аргументов, восстанавливает `ip` и `fbase` и применяет режим вызова (`finish_call`). Возврат из функции 0 завершает программу: результат — код завершения.

**Режим вызова** — байт после команды вызова (формат байт-кода, разд. 3.4): `$80` — результаты отбросить; `$40 + n` — ровно `n` значений; `n` — число целей, и если целей на одну больше, чем результатов, последней кладётся `null` (нет ошибки). Для методов число результатов становится известно только при выполнении, поэтому совпадение проверяет `finish_call` (`wrong number of results`).

**Встроенные функции и методы.** `callb` берёт функцию из `bfuncs[id]`, `callm` — из таблицы типа получателя (`mt_str`, `mt_arr`, …); пустая запись — `no method m for type`. Функция читает аргументы через `arg_int`, `arg_str` и подобные (неверный тип — ошибка выполнения), кладёт результаты через `res(k, t, v)`, а `bn` — их число. Результат функции: 0 — успех, 1 — ошибка в `cur_err`. После вызова стек временных корней сбрасывается.

### 5.4. Ошибки

- **Ожидаемая ошибка.** Встроенная функция вызывает `fail_code(код, объект)`: создаётся объект-ошибка с текстом из таблицы `err_texts` и местом текущей команды, он ставится в `cur_err`. Коды `FAULT`, `BADF`, `NOSYS`, `AGAIN` превращаются в ошибку выполнения `internal error`, код `INTR` — в завершение с `$8001`.
- **Перехват** (`call_failed`): если режим вызова — «результаты + 1», на стек кладутся `null` на место результатов и ошибка, `cur_err` очищается.
- **Раскрутка** (`fail_current`): иначе снимаются кадры, пока не найдётся вызов с перехватом; кадр с перехватом получает ошибку так же. Дошла до функции 0 — `top_error` выводит `имя: объект: текст` и завершает процесс с кодом 1.
- **`fail`.** `op_fail` читает операнды и место команды, пока в окне кадр модуля, затем собирает ошибку в оверлее `gc` (`g_fail`) и раскручивает стек.
- **Ошибка выполнения** (`rt_err2`): текст копируется в ближний буфер (он мог лежать в образе оверлея), запоминаются место и имя функции, в окно возвращается кадр модуля, и оверлей `sys` выводит `bsvm: файл:строка: in function имя: текст`, читая таблицу строк из `.bsc`. Затем `do_exit(125)` записывает буферы.

### 5.5. Код в нескольких кадрах

У модуля больше 8 КБ код лежит в кадрах по 8 КБ, а в окне 6 стоит тот, что выполняется (`cf_cur`). Смещение кода `off` превращается в адрес функцией `code_at`: кадр `off >> 13`, адрес `$C000 + (off & $1FFF)`; если нужного кадра нет в окне, он ставится туда `XMAP`. Переход, выводящий за окно, пересчитывается через `code_at`. Команда никогда не пересекает границу кадра: компилятор ставит перед границей `jmp` на начало следующего кадра. Кадры вызовов хранят смещение возврата, а не адрес, поэтому возврат в другой кадр тоже идёт через `code_at`.

## 6. Куча

### 6.1. Handles

Байт-код и значения не содержат адресов: ссылка на ближний объект — 15-битный номер handle. `htab[h]` — адрес заголовка объекта, `hseg[h]` — где он (`HS_NEAR` — ближняя куча или статический объект; `HS_OWN5` — собственный кадр страницы 5; `HS_FWD` — перенесён, в `htab[h]` дальняя ссылка). Свободные записи образуют список: `(следующий << 1) | 1`. Handle 0 не используется и означает «нет ссылки».

Число handles задаётся при запуске: одна запись на 22 байта кучи. Исчерпание handles равносильно нехватке памяти.

### 6.2. Выделение

`alloc(тип, размер)` берёт место с вершины кучи (`heap_top`) и свободный handle. Если не хватает места или handles:

1. обычная сборка (`gc`);
2. если и после неё не хватает, а расширенный режим ещё выключен, — переход в него (оверлей `gc`, разд. 7.2);
3. в расширенном режиме — выделение сразу в дальней памяти (`far_alloc`) и поднятый флаг `promote_pending`, чтобы в ближайшей безопасной точке перенести ближние объекты;
4. места нет нигде — ошибка выполнения `out of memory`.

`new_str` отвергает строки длиннее 32 767 байт (`too large`).

### 6.3. Правило доступа

Любое выделение может запустить сборку и сдвинуть объекты, а в расширенном режиме — сменить кадр в окне данных. Поэтому:

- вне `heap.b16` и `map.b16` к данным объекта обращаются только функциями кучи: `hgw`/`hsw` (слово), `hgb`/`hsb` (байт), `hget`/`hput` (обмен с ближней памятью), `hmove`, `hcmp`, `hfind`, `hfill` (между объектами), `aget`/`aput` (элементы массива);
- адрес данных, полученный от `hp()`, годен только до следующего вызова любой функции кучи, и одновременно используется адрес только одного объекта;
- встроенная функция хранит через выделение только handle, а handle созданного, но ещё не доступного из корней объекта кладёт в стек временных корней (`tpush`, 16 записей); `op_callb` и `op_callm` сбрасывают его после вызова.

Пример ошибки, которую правило исключает: `split` создал массив, следующая подстрока запустила сборку, и массив, ещё не видимый из корней, был бы собран.

Ближняя память — стек значений, глобальные, буферы файлов, локальные массивы функций B16 — объектом не является и не двигается.

`hmove` и `hcmp` для объектов в разных кадрах дальней памяти копируют и сравнивают через ближний буфер `bounce` по 128 байт (`hpair` сообщает, видны ли оба объекта сразу).

### 6.4. Сборка ближней кучи

Сборщик — mark-compact, без поколений в обычном режиме.

- **Корни:** стек значений от `vs` до `vsp`, глобальные, временные корни, `cur_err`, строка построителя (`bld_h`); в расширенном режиме — ещё ссылки запомненных дальних объектов. Константы модуля статичны и не помечаются.
- **Пометка** не рекурсивна: явный стек на 48 ссылок (`mstack`). При переполнении объект получает `F_SCAN`, и после основного прохода `rescan_all` просматривает кучу, пока такие объекты есть.
- **Просмотр объекта** (`scan`): элементы массива, ключи и значения записей словаря, ссылки кусков, текст и объект ошибки, путь файла. Строки не просматриваются.
- **Сжатие** (`compact_near`): живые объекты сдвигаются вниз, `htab` исправляется по полю `h` заголовка. Handle мёртвого объекта освобождается; мёртвый файл перед этим закрывается (`file_finalize`: запись буфера и `CLOSE`, ошибка теряется). Фрагментации нет.

Проверка правила 6.3 — сборка `GC_STRESS`, где сборка выполняется перед каждым выделением (`make stress`): все тесты и примеры должны дать тот же вывод.

## 7. Дальняя память

Когда сборка не находит места в ближней куче, VM переходит в **расширенный режим** и размещает объекты в кадрах расширенной памяти. Программа, которой хватает ближней кучи, его не касается: в обычном режиме функции доступа проверяют один признак `fastpath`.

### 7.1. Ссылки

| Вид | Биты | Значение |
| --- | --- | --- |
| ближняя | бит 15 = 0 | номер handle (разд. 6.1) |
| дальняя | бит 15 = 1 | биты 14–8 — сегмент (1…127), биты 7–0 — индекс в таблице сегмента |

**Сегмент** — кадр 8 КБ. Его первые 512 байт — таблица на 256 записей: смещение объекта в кадре или пересылка (бит 0 = 1). Объекты лежат за таблицей, поэтому объект в дальней памяти — не больше 7674 байт данных. Предел — 127 сегментов (около 1 МБ) и не больше 32 512 объектов; столько VM берёт сверх своей памяти, чтобы оставить память дочерним процессам.

Ближняя ссылка не меняется, пока объект ближний; дальняя не меняется никогда. Поэтому правило доступа 6.3 остаётся тем же: адрес годен до следующего вызова функций кучи, ссылки — всегда. `oaddr(r)` по ссылке ставит нужный кадр в окно данных (страница 5) и возвращает адрес заголовка.

### 7.2. Переход в расширенный режим

`far_activate` (оверлей `gc`): объекты выше `$A000` остаются на месте как сегмент «собственный кадр страницы 5» (`HS_OWN5`, виден в окне при `XM_OWN`); объект, пересекающий границу, копируется в дальний сегмент через `bounce`; ближняя куча заканчивается на `$A000`, а страница 5 становится окном данных. Ссылки при этом не меняются. В расширенном режиме ближняя куча — около 3,6 КБ.

### 7.3. Поколения и перенос

- Новые объекты создаются в ближней куче. Если её не хватает внутри встроенной функции, объект создаётся сразу в дальней памяти.
- **Перенос** (`promote`) копирует все живые ближние объекты в сегменты и заменяет ссылки на них дальними: в корнях, в запомненных дальних объектах и в самих перенесённых объектах. Перенесённые объекты просматриваются по порядку размещения, как в алгоритме Чейни. Объекты больше сегмента остаются ближними, их ссылки исправляются отдельно. После переноса handles перенесённых объектов освобождаются, и выполняется обычная сборка остатка.
- Перенос меняет ссылки, поэтому выполняется только в безопасных точках (разд. 5.2).
- **Обычная сборка** просматривает только ближнюю кучу. Дальние объекты, в которые записана ссылка на ближний объект, запоминает **барьер записи** (`wbar`, `hset_ref`: элементы массивов, записи словарей, поля ошибок и файлов) в списке на 128 объектов; их ссылки служат корнями. При переполнении списка (`rem_all`) просматриваются все дальние объекты.
- **Полная сборка** (`major_gc`) помечает все объекты, освобождает записи таблиц сегментов, закрывает мёртвые файлы и сжимает кадры. Она выполняется перед переносом, если в дальней памяти не хватает места или свободных записей.

### 7.4. Цена

Переключение окна — около 50 команд с обёрткой B16 (в мониторе около 38: быстрый путь `XMAP`). Цикл, который поочерёдно обращается к куску массива и к строке в другом кадре, медленнее обычного режима примерно в 1,6 раза: проход по массиву строк — 1,96 тыс. команд на элемент против 1,21 тыс.

### 7.5. Массивы и словари

**Массив** хранит длину и элементы по 4 байта. Данные до 4 КБ лежат в самом объекте; больше — в кусках по 4 КБ (`F_CHUNK`, кусок `TY_VCH` — 1024 значения): за постоянными полями — число кусков и их ссылки. Каждый кусок — отдельный объект и может лежать в своём кадре; рост массива добавляет кусок без копирования. `delem` вычисляет адрес элемента по номеру, а `dobj` — объект, в котором он лежит (для барьера записи). Предел — 32 767 элементов.

**Словарь** — хеш-таблица с порядком вставки (`map.b16`):

- постоянные поля: `count` (живых записей), `used` (занятых, с удалёнными), `cap` (записей), `nb` (корзин, степень двойки, не меньше `2 · cap`);
- записи по 8 байт: ссылка на ключ, хеш, значение (`Val`) — в порядке вставки, поэтому `keys()` и `values()` выдают порядок вставки без сортировки;
- корзины — номера записей + 1 (0 — пусто), открытая адресация с линейным пробированием;
- хеш строки — djb2 (`x = x · 33 + байт`, начало 5381);
- удаление ставит ключу 0; корзина остаётся и пропускается при поиске. При заполнении словарь перестраивается (`map_rebuild`) с живыми записями по порядку;
- в обычном режиме у словаря без кусков `map_find` идёт по прямым адресам, без функций доступа;
- больше 4 КБ — куски записей (`TY_ECH`, 512 записей) и корзин (`TY_BCH`). Предел — 16 384 ключа.

## 8. Ввод-вывод

Таблица `slots` на 11 записей в закреплённой памяти VM: 0 — поток 0, 1 и 2 — потоки 1 и 2, 3–10 — файлы программы (отсюда предел 8 открытых файлов). Запись — дескриптор, режим, буфер 192 байта, позиция чтения, признак конца, признак консоли и отложенная ошибка записи.

- **Запись** буферизуется; буфер записывается, когда полон, при `\n` в поток-консоль, по `flush`, перед чтением потока 0 и запуском программ, при завершении. Ошибка `WRITE` запоминается и возвращается следующим `write`, `flush` или `close`.
- **Объект `file`** хранит номер записи и путь. Буферы не в куче, поэтому сборщик их не двигает, а обработчик Ctrl+C может их записать.
- **Нехватка дескрипторов.** При `MFILE` от монитора `open_gc` запускает сборку (она закрывает недостижимые файлы) и повторяет `OPEN`.
- **Построитель строк** (`bld_start`, `bld_put`, `bld_done`) собирает результат чтения неизвестной длины: буфер-строка удваивается до 32 767 байт; он — корень сборщика (`bld_h`).
- **Ctrl+C.** Обработчик `on_break` вызывает `flush_all` и завершает процесс с `$8001`. Он не выделяет память и не выполняет байт-код. `slot_flush` обнуляет счётчик буфера до `WRITE`, чтобы обработчик не записал тот же буфер второй раз.

## 9. Оверлеи

Резидентной части не хватало места для кучи: первая версия, целиком резидентная, занимала 38 КБ с bss и оставляла куче около 12,5 КБ при ожидавшихся 16–24 КБ. Редкий и долгий код библиотеки вынесен в оверлеи — образы по адресу окна 6, которые лежат в `bsvm.ovl`.

| Оверлей | Содержимое | Образ |
| --- | --- | --- |
| `fs` | пространства `fs` и `path` | 5,5 КБ |
| `sys` | `proc`, `time`; `str.hex`; методы `replace`, `equal_fold`, `repeat`, `reverse`, `sort`, `keys`, `values`, `clone` словаря; сообщение об ошибке выполнения, `e.where()` | 6,6 КБ |
| `gc` | переход в расширенный режим, перенос, полная сборка, выделение в дальней памяти, куски; `fail`, `error()` | 5,6 КБ |
| `init` | загрузчик модуля; собран по адресу страницы 5 и выполняется один раз | 3,3 КБ |

**Граница.** Резидентно всё, что вызывается в цикле на каждый элемент и работает недолго: частые методы строк, массивов, словарей, файлов и ошибок, `io`, глобальные функции. Там два переключения окна были бы сравнимы с самой работой. В оверлеях — то, что вызывает монитор (тысячи команд на вызов) или выполняется редко.

**Вызов.** Таблицы `bfuncs` и `mt_*` указывают на заглушки, которые генерирует `mkovl.py`: `fn имя(): uint { return ov_call(OV_x, i) }`. `ov_call` запоминает, что стоит в окне, ставит туда кадр оверлея (при первом вызове выделяет кадр и читает образ из `bsvm.ovl`), вызывает вход `i` из таблицы `ov_table` образа и возвращает в окно прежнее: кадр модуля, текущий кадр кода или другой оверлей. Вызов стоит около 100 команд сверх работы функции (два `XMAP`); до быстрого пути `XMAP` в мониторе — около 700. В примерах переключения занимают меньше 0,5 % времени.

**Вложенные вызовы.** Оверлей может вызвать функцию другого оверлея (сборка при выделении памяти в `fs.read_text`): по возврату в окне снова прежний оверлей. Поэтому функции, вызываемые так, не получают указателей на данные вызывающего оверлея и не читают таблицы модуля из окна: операнды команды и место ошибки читает резидентная часть до вызова. Оверлеи обращаются к объектам только через функции кучи.

**Отказы.** Нет файла `bsvm.ovl` — `bsvm: путь: cannot open`; испорчен — `bad overlay file`; нет кадра — `not enough memory`; во всех случаях код 126.

**Формат `bsvm.ovl`.** Заголовок: `"BS"`, число образов, пары «смещение, длина» каждого. Образ: слово `"OV"`, адрес таблицы входов `ov_table`, затем код и данные, собранные по адресу окна.

**Сборка** (`tools/mkovl.py`):

1. `stubs` — заглушки входов оверлеев для резидентной части;
2. `keep` — список резидентных функций, которые вызывают только оверлеи, чтобы они попали в образ;
3. резидентная часть собирается и даёт карту памяти `bsvm.map`;
4. `env` — объявления резидентной части для оверлеев: функции как `extern fn`, глобальные как `var ИМЯ at АДРЕС`;
5. `overlay` — каждый оверлей собирается по адресу окна (`init` — по `$A000`) с метками резидентных функций из карты;
6. `pack` — файл `bsvm.ovl` в порядке номеров `OV_*`.

## 13. Принятые решения

| Решение | Почему | Отвергнутая альтернатива |
| --- | --- | --- |
| значения по 4 байта с тегом в старшем слове | копирование двумя словами; место для `ulong` фазы 2 без смены формата | значения переменной длины |
| handles вместо адресов | объекты можно двигать: mark-compact без фрагментации; дальние объекты прозрачны для байт-кода | адреса в значениях с неподвижной кучей |
| mark-compact с явным стеком пометки | рекурсия B16 съела бы стек 1,5 КБ; повторный просмотр кучи при переполнении стека редок | рекурсивная пометка |
| буферы файлов вне кучи | обработчик Ctrl+C пишет их без выделения памяти и без кучи | буферы-объекты |
| редкий код — в оверлеях | ближняя куча выросла с примерно 12,5 КБ и сохранила место для дальней памяти | целиком резидентная VM; «липкий» оверлей с кодом модуля в ближней памяти — отнял бы у кучи размер модуля ради 3 % |
| дальняя память с поколениями и барьером записи | предел данных — 1 МБ, а не 48 КБ процесса; обычный режим почти не платит | вся куча в кадрах с самого начала |
| быстрый путь `XMAP` в мониторе | расширенный режим медленнее обычного в 1,6 раза вместо 3–5, вызов оверлея — 100 команд вместо 700 | второе окно данных ценой страницы ближней памяти |
| таблица строк читается из файла | не занимает память; нужна только для сообщений | загрузка таблицы строк |
| неустойчивая быстрая сортировка | не требует второй копии массива: память кучи — главный ресурс | сортировка слиянием |
